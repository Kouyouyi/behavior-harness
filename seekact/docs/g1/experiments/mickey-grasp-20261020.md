MCP 大多提交异步任务，3.80 秒不包含动作实际执行。
32 + 54.04 + 30 秒也不包含交接、停稳、热响应、图像理解、推理和现场等待。
因此不能宣称其余 24 分钟都是 LLM 耗时，也不能用这些数字宣称加速倍数。
应优先减少逐次工具选择、轮询与重复解释，把必要视觉判断和现场信息保留在检查点。

可复用经验：

1. 先确定合适的抓取方向，再做最后接近和 prepare。此次大幅转向后成功，
   是值得复测的姿态条件，不足以证明必须左转 87°、或者右手永远优于左手。
2. 移动会使 VLA 初始化失效。尽量将移动安排在 prepare 前，减少重复准备；
   必须移动时重新检查，不能复用旧初始化。
3. prepare 会张开双手，需要当前空手和抬臂净空依据，不能作为通用失败重置。
4. 抓起时及时暂停、保持，再用不同源帧确认。动作预算完成和抓取成功独立记录。
5. 遮挡时返回不确定；不能把未看见玩偶推断为掉落。
6. 现场确认绑定当时区域和姿态。不能将本轮“不会碰撞”迁移成下一轮永久许可。

## 可执行部分

[mickey_workflow.py](../../../examples/g1/mickey_workflow.py)提供：

- `move(direction, duration_s, yaw_rate_deg_s)`：当前图像检查 → 单段提交 →
  Python 自动查询结果 → 要求 completed 和 settled → 返回新图像。
- `prepare()`：空手/抬臂净空检查 → 准备并等待完成 → 新图像。
- `grasp()`：可达/接近路径检查 → 最多 750 步 → 运行中视觉检查 →
  看见持物或出现不确定时暂停本次任务 → 两张不同源帧验收。

所有调用走传入的 `ctx` 和现有 owner，没有额外身体发布器。
session 变化、旧图像、动作失败、热响应中断均返回检查点，不自动重试。
代码不发送 O、不终止底层进程；抓取异常时只尝试暂停自己提交的活动任务。
移动结果超时则报告 job ID，调用方应核查是否仍在运动。

`review(stage, observation)` 必须由实际查看图像的 Agent/视觉适配器实现。
返回 `frame_id`、`evidence` 和对应判断；不能用恒真函数替代视觉检测：

| 检查点 | 所需判断 | 未通过 |
|---|---|---|
| before_move | path_clear | 不提交移动 |
| before_prepare | hands_empty、arm_clear | 不张手、不准备 |
| before_grasp | target_reachable、approach_clear | 不提交抓取 |
| during_grasp | held；否则 continue 明确为 true 才继续 | 暂停当前抓取并复查 |
| verify_hold / verify_hold_again | held，且两个不同相机源帧 | 不宣称抓取成功 |

调用示例（在提供真实 `review` 的既有 Agent 会话内）：

```python
from examples.g1.mickey_workflow import MickeyWorkflow

flow = MickeyWorkflow(ctx, review=review)
# 按当前场景选择移动段；每段返回后检查新图像再决定下一段。
# flow.move("right", duration_s=2)
# 最后移动完成且视觉确认条件满足后：
flow.prepare()
report = flow.grasp()
# flow.records 保存每个判断、观测和结果，可交由会话写入运行记录。
```

这是基础 Python 编排接口。后续已通过下面的 MCP 编译步骤接入 UI，
由原有 Agent 直接看图，不需要另开视觉服务；整条路线仍依据当前画面选择。
基础同步视觉回调如果耗时过长，会延迟提前暂停；底层仍限制为 750 步。

## UI 编译执行入口（本次加速版）

`harness/codex_cli/task_steps.py` 已接入原有 `ui_bridge`，
新增 `g1_task_step`。启动后的 UI Agent 默认优先使用它：

1. `observe`：一次返回当前图像、owner 和消息。
2. `move` / `prepare`：检查已观察的 frame_id、条件和证据，提交一次，
   Python 等待完成，直接带回下一张图，省去模型逐次轮询。
3. `grasp`：提交 750 步，约 2 秒后带图返回；`check` 继续等待并观察，
   看到抓起或出现不确定时用 `pause` 保持。
4. `confirm_hold`：两个不同且新鲜的源帧都经 Agent 确认持物后，
   独立记录视觉成功，不修改底层 `task_success_verified=false`。

每个动作使用持久化 request_id；桥接器重连不重放已经提交或结果未知的动作。
每个轮次保存 `ui-agent-turns/<batch>/compiled-task.json`，记录工具结果、
检查帧、当前 job、视觉验收和时间预算。新 UI 消息会中断内部等待，
暂停该编排拥有的上层动作，再交给 Agent 处理。

目标 180–300 秒，单轮预算 600 秒，从 UI Agent 启动该轮开始计时，
包括图像推理和步骤等待；模型/相机/原生启动时间另计。10 分钟不是停机定时器：
超时结束该轮 Agent 推理并请求暂停 VLA/移动，保留原生控制与持物目标，
不发送 O、不终止 owner/native、不停电机。现场停机由用户决定。
该预算按一个 UI dispatch 计算，用户后续新任务会开始新轮次，不能宣称跨轮总计小于10分钟。

原生/owner 不需为这个编排工具改动动作接口；新 UI Agent 进程加载加速入口。
不能启动第二个并行控制 Agent。启动命令仍为 `bash scripts/start_g1_experiment.sh`，
就绪后 UI 输入“抓取桌上的米老鼠，按加速流程执行，抓起后保持”。
现场空手、净空等依据必须来自当前观察或用户当前确认。

   每次不超过原动作半时长且不超过1秒，之后重新测量。改善不足1度立即交回恢复，避免重复弱指令。
